# ADR 0001. Изоляция внешнего Lua

**Статус** — предложено. Изменение worker, протокола и формата доказательства установки требует согласования. Загрузка Lua-кода из установленных пакетов остаётся закрытой.

## Контекст и результат аудита

Core использует изолированный неэкспортируемый `LuaPluginService`. `AndroidLuaPlugins` привязывает именованный экземпляр через `bindIsolatedService`, проверяет UID ответа и ограничивает своё ожидание пятью секундами. Сервис проверяет UID запроса, а Messenger переносит Bundle с ограниченными данными. Таймаут и отвязка сами по себе не подтверждают смерть процесса. `TrustedLuaRuntime` ограничивает исходник, глубину вызовов, количество инструкций, вызовы Plugin API и вывод. LuaJ не даёт жёсткой квоты своего участка JVM-кучи. `TilePluginSession` уже ограничивает частоту событий, видимые кнопки и состояние экземпляра. `TileUi` валидирует дерево, а Core повторяет проверку после Binder. [Runtime](../LUA_RUNTIME.md) · [Tile API](../TILE_PLUGIN_API.md) · [Изолированный сервис Android](https://developer.android.com/guide/topics/manifest/service-element#isolated)

Package Manager проверяет подпись каталога, привязку версии к URL и SHA-256, отдельную подпись архива, ограничения ZIP и манифест. После распаковки он удаляет временный ZIP. Реестр схемы 1 содержит манифест и имя директории. Он не сохраняет оригинальный подписанный ZIP или подписанные хеши отдельных файлов. Совпадение ID, версии и существующего файла поэтому не доказывает идентичность исполняемых байтов. [Package Manager](../PACKAGE_MANAGER.md) · [Аудит v0.5](../EXTERNAL_PLUGIN_SYSTEM.md)

## Предлагаемое решение

Использовать PUC Lua 5.4 только для нового внешнего worker. Эта VM даёт контроль каждой аллокации Lua, а компилятор текстовых chunk использует тот же аллокатор. Сохранить LuaJ для существующего DroidFetch и терминального `lua run`. Закрепить проверенный исходный релиз и SHA-256 при добавлении нативной зависимости, сохранить лицензию и обновлять версию по результатам security review.

### Worker и квоты

- Один экземпляр внешнего worker на активный тайл, отдельный изолированный UID и имя привязки. Лимит двух одновременно активных экземпляров для первого релиза. Worker не получает Android Context в Lua, путь к приватному хранилищу, URL, пользовательские Binder-объекты или произвольные привилегии. Системные данные передаются как DTO только после проверки Core.
- Только текстовый режим `luaL_loadbufferx(..., "t")`, отдельное состояние на сессию и отсутствие стандартных библиотек, `require`, динамической загрузки и shell. Для Hello Tile предложен `__add` для ограниченной десятичной строки и неотрицательного целого с проверкой переполнения. Остальные операции требуют явного контракта совместимости. Библиотека `string` не открывается.
- Предлагаемые стартовые пределы для измерения на Pixel 9 — 2 МиБ фиксированной арены VM с метаданными внутри квоты, исходник до 16 КиБ, 50 000 инструкций на команду, измерение CPU-времени потока до 100 мс на команду, один запрос в полёте и интервал событий не менее 350 мс. Ограничить отдельно нативный мост, JNI-буферы и размер кадра. Квота VM не является лимитом RSS Android-процесса. Ошибки аллокации и Lua longjmp остаются внутри защищённой функции C; Kotlin получает код результата.
- Перед парсингом и перед обработкой события поставить таймер ядра с `CLOCK_MONOTONIC` и `SIGKILL` для собственного процесса. Предложенный первый дедлайн — 1 с на команду. При ошибке постановки таймера запуск запрещён. Предусмотреть такой же независимый ограничитель на закрытие или потерю клиента, если worker занят. Core не посылает сигнал чужому UID по PID и считает остановку подтверждённой только после Binder death. При таймауте Core прекращает принимать старые кадры, ограничивает повторы и не освобождает слот для нового процесса до подтверждения смерти. Проверить на Pixel 9, что таймер и смерть Binder наблюдаются в реальном isolated service; успешный Termux-тест этого не доказывает. [Bionic timer API](https://android.googlesource.com/platform/bionic/+/main/libc/include/time.h) · [Binder death](https://developer.android.com/reference/android/os/IBinder#linkToDeath(android.os.IBinder.DeathRecipient,int))

### Связь пакета и фактического исходника

- Расширить существующий атомарный реестр доказательством установки. В одной транзакции сохранить проверенный оригинальный архив и подписанный конверт с точной записью каталога. Существующие записи читаются как установленные данные без права исполнения. При повторной установке той же версии с явным подтверждением можно заполнить доказательство из уже опубликованного оригинального артефакта. Без сети старую запись без доказательства нельзя автоматически повысить до исполняемой.
- Перед каждым созданием сессии проверить запись и текущий статус пакета, подписанное доказательство, подпись и хеш того же сохранённого архива, API и явное разрешение `ui.tile`. Из проверенного архива вывести ожидаемые SHA-256 и размер исполняемого файла. Хешировать точные распакованные байты, из которых создаётся неизменяемый снимок. Первоначально разрешить только entry, без импортов. Внешний worker не получает путь на диске, а повторное чтение по пути после проверки запрещено.
- Удаление и отзыв инвалидируют поколение сессии до удаления файлов, прекращают события и закрывают привязку. Кадр проверяется на то же поколение перед применением. Повторная привязка после сбоя начинает новый сеанс из вновь проверенного снимка. Для первой версии допускать только утверждённый first-party Hello Tile, с минимальным разрешением `ui.tile`. Отзыв из свежего каталога блокирует сессию, сохранённый офлайн-кэш может задержать обнаружение отзыва.

### Типизированный IPC

Протокол AIDL передаёт пять типов сообщений. Примитивные поля фиксированной ширины и небольшие DTO имеют ограниченные размеры, а большие данные принимаются только через узкие read-only дескрипторы. Для исходника Core передаёт дескриптор неизменяемого снимка после закрытия всех writable mappings, без текста в Parcel, произвольных команд, классов или объектов исполнения. Worker проверяет длину и закрывает дескриптор. Core проверяет ID и поколение сессии, UID канала и размер дерева до декодирования кадров. Обе стороны валидируют последовательность и права. [AIDL](https://developer.android.com/develop/background-work/services/aidl)

| Сообщение | Поля и правило |
|---|---|
| `CreateSession` | Версия протокола, ID сессии, поколение, версия API, разрешённые DTO, размер исходника и дескриптор снимка. Допускается только при создании. |
| `Render` | ID, поколение, номер запроса, ограниченное дерево `TileUi` и состояние до 512 единиц UTF-16. Допускается один ответ на запрос. |
| `DispatchEvent` | ID, поколение, номер запроса и ограниченный ID видимой кнопки. Core и worker проверяют принадлежность текущему дереву, частоту и отсутствие другого запроса. |
| `DisposeSession` | ID и поколение. Идемпотентная остановка, инвалидация последующих сообщений и очистка ресурсов. |
| `Error` | ID, поколение, номер запроса и перечислимый код, например `DENIED`, `QUOTA`, `TIMEOUT`, `INVALID_INPUT`. Без дампа памяти или частных данных. |

## Проверки и ворота допуска

Локальный эксперимент вне APK на Termux ARM64/Bionic использовал Lua 5.4.9 из архива с проверенным upstream SHA-256. Скачанный опубликованный Hello Tile сверили по SHA-256. Счётчик остановил бесконечный цикл, аллокатор отклонил рост таблицы с пиком 65 522 запрошенных байта при лимите 65 536, а независимый таймер завершил отдельный зацикленный процесс сигналом SIGKILL. В пустой Lua 5.4 VM опубликованный модуль показал начальный экран, но Increment завершился ошибкой арифметики со строкой. Узкий адаптер позволил пройти Increment и Reset без открытия стандартных библиотек. Проба измеряет запрошенные Lua байты через realloc. Фиксированная арена, APK, SELinux isolated service, Binder и восстановление ещё не тестировались этим экспериментом. [Исходник Lua 5.4.9 и SHA-256](https://www.lua.org/ftp/) · [Опубликованный Hello Tile](https://github.com/PseudoEF/HyprDroid-Packages/releases/tag/hello-tile-v1.0.0)

До включения маршрута проверить изменённый или повреждённый entry, подмену доказательства установки и отказ в разрешении. Проверить цикл, превышение памяти, сбой JNI, невалидный Parcel, переполнение событий, поздний кадр после удаления и отзыв во время исполнения. На Android подтвердить Binder death и освобождение слота, восстановление после аварии, независимость двух тайлов и работу лаунчера после сбоя. До прохождения ворот приложению следует отвечать отказом на `hypr tile add hello-tile`.

## APK и Pixel 9

Текущая ветка содержит документацию. Для совместимого CI после отправки ветки используется штатный workflow Core:

```sh
gh workflow run android.yml --repo PseudoEF/HyprDroid --ref feature/safe-external-lua-runtime
```

Workflow собирает unit, debug и androidTest APK. Ручной запуск содержит штатный этап подписанного распространения с существующим ключом APK и выделением `versionCode`. Для будущего worker потребуется закреплённый NDK в workflow, ARM64 и x86_64, проверка 16 КиБ страниц и тестовый путь имитации аварий, недоступный релизной сборке. Ключ APK и ключ издателя пакетов остаются раздельными. [Действующий workflow](../../.github/workflows/android.yml) · [Правила обновления](../UPDATING.md)

На Pixel 9 для текущей сборки проверить `hypr repo update`, `hypr install hello-tile`, `hypr list --installed` и контролируемый отказ `hypr tile add hello-tile`. В будущей сборке-кандидате после допуска создать два тайла, нажать Increment и Reset только в одном, удалить активный тайл и убедиться в освобождении worker. Затем прогнать тестовые цикл, OOM и смерть Binder; JVM и Termux-проверки не заменяют этот прогон.
